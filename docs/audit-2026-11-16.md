## New findings

### TABAK-008: Android price input drops the decimal comma (Medium)

**Where:** [SettingsScreen.kt:858-859](../composeApp/src/commonMain/kotlin/com/tabakpp/app/composeapp/ui/screens/SettingsScreen.kt#L858) (filter) and [:920-925](../composeApp/src/commonMain/kotlin/com/tabakpp/app/composeapp/ui/screens/SettingsScreen.kt#L920) (parse). The preview math at `:805-810` has the same issue.

**What happens:**

1. The pack and pouch price field uses `KeyboardType.Decimal` and filters input to `isDigit() || '.'`.
2. On a keyboard with a comma decimal separator (common in German, Dutch and French layouts; the app's currency is €), the comma is silently removed. Typing `6,50` leaves `650` in the field.
3. Saving with 20 units per pack stores `unitPrice = 32.5` instead of `0.325`. That's within the rule bound (`unitPrice <= 1000`), so Firestore accepts it.

From then on, every spent, saved and budget figure is 100× too large. Folded days also carry it into `lifetimeAggregates`.

**Also:** input like `1.2.3` parses to `null`, which falls back to `0.0` without telling the user.

**Contrast:** `TrackerForm.kt:239` and web `ProtocolFormOverlay.jsx:65` both do `.replace(',', '.')`. Web Settings uses `<input type="number">`, where the browser normalises the separator. Only the Android Settings path is affected.

**Fix (S):**

- Accept `,` in the filter, normalise it to `.`, and allow at most one separator.
- Disable Save, or show an error, when the value doesn't parse instead of saving `0.0`.
- Add a unit test for `"6,50"` → `6.5`.

**Resolution (#165, `3f055d0`):** `InputSanitizer.decimalInput` treats `,` as the separator and keeps only the first one. `InputSanitizer.parseDecimal` accepts either separator. Settings uses both for the filter, the preview and Save. Covered by `DecimalInputTest`. Empty input still saves `0`; with the new filter that's the only unparseable value left.

### TABAK-009: Unbounded pouch fields on Android (Low)

`SettingsScreen.kt:924-925` coerces `pouchPrice` only `>= 0` and `estimatedYield` only `>= 1`. The rules cap them at 10 000 (`firestore.rules:316-317`), so larger values are rejected and the user sees the generic save error. The pack path already clamps quantity to 1..1000. Clamp the pouch fields the same way, or show an inline error.

**Resolution (#165, `d9df6b5`):** `costSettingsFromInput` clamps every field to the rule bounds (unitPrice 0..1000, unitsPerPack 1..1000, pouchPrice 0..10000, estimatedYield 1..10000). The unit-cost preview and Save share it. Covered by `CostSettingsInputTest`.

### CI-7: Dependabot alerts disabled (Low)

`gh api …/dependabot/alerts` returns "Dependabot alerts are disabled for this repository". `.github/dependabot.yml` only opens version-bump PRs, so a CVE in a pinned version you haven't bumped yet goes unreported. Turn it on in **Settings → Code security → Dependabot alerts**. It's free and needs no code change.

**Resolution (2026-11-16):** alerts enabled through `PUT /repos/shareef01/tabakpp/vulnerability-alerts`. `GET` now returns 204.

## Review of changes since the last audit

### v1.0.15: day-status backfill (#163)

- **Rules:** `validDayShape` now requires `status`, but only on **create**. `validDayUpdate` checks changed fields only, and now reads `before.get('status','open')`, so legacy status-less docs stay updatable. Every create path on both platforms sets `status: 'open'`:
  - web `registryService.js:384, 847`, `dailyLedger.js:325`
  - Kotlin `FirebaseRegistryRepository.kt:423, 669, 1181`
  - Older APKs encode the `DayDocument.status = "open"` default.

  So there's **no compatibility break for older installed APKs**.
- **Backfill:** both platforms are resumable through `meta/dayStatusBackfill`, with compare-and-set on the marker. They're bounded at 10 × 200 docs per call, skip MIGRATING/OPTION_B accounts, and are covered by a new rule clause.
  - After completion each call costs one read.
  - The first run does one transaction per status-less doc, sequentially. That's acceptable as a one-time cost.
- **Double-credit check:** a backfilled day is then closed and folded. I checked whether such days could already be in `lifetimeAggregates`:
  - Pre-v1.0.14 Android scanned all days and closed status-less ones, which set `status: closed`, so they aren't picked up again.
  - Web's `status == 'open'` query never matched them, so they were never folded.
  - `closeDay` skips the fold when `foldedIntoLifetime` is true.

  No double count found. `testD3c` checks fold-once.
- Minor asymmetry: web has a `nextDate <= afterDate` no-progress guard that Kotlin lacks. It's harmless because the page cap bounds the loop.

### v1.0.16: startup and Insights (#164)

- `RegistryViewModel` now clears `loading` as soon as the profile for **the current uid** arrives. `ensureUserDocument` and the migrations finish in the background, in the same `coroutineScope`, with `CancellationException` re-thrown.
  - `sessionProfile` pairs the profile with its uid, so a previous account's profile can't be shown after switching accounts.
- **New exposure checked:** the UI is now interactive while `migrateSmokingUnitsIfNeeded` may hold its 120 s lease.
  - Writes are blocked by the rules (`accountWritable`), and the VM pre-checks the lease with the same "History migration is in progress" message as web (`RegistryViewModel.kt:730-734`).
  - The migration's absolute `smokingUnits` write can't race a fold, because day writes are denied while the lease is held.
  - No defect.
- The Insights crash fix removes the nested `verticalScroll` inside the History `LazyColumn`. Monthly aggregation is now `remember`ed. Chart labels use `weight(1f)`. The rest is copy changes only.
