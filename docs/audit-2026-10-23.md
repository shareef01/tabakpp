## Findings, most severe first

### H1 — The Android `staging` build type does not compile (confirmed)

`staging` uses `initWith(getByName("debug"))`. That copies the build-type *settings* but not the `src/debug` *source set*. `TabakApp.kt:25` calls `AppCheckInstaller.install()`, which exists only in `src/debug` and `src/release`. With a valid-shaped `src/staging/google-services.json` in place, `./gradlew :androidApp:compileStagingKotlin` fails:

```
e: androidApp/src/main/java/com/tabakpp/app/TabakApp.kt:25:9 Unresolved reference 'AppCheckInstaller'.
```

`src/debug/AndroidManifest.xml` and `network_security_config_debug.xml` are also absent from staging. The variant cannot be used for Android staging QA, although PHASE_8 records the build type as added. CI never builds this variant, so the break went unnoticed.

**Fix:** add `src/staging/java/com/tabakpp/app/AppCheckInstaller.kt`. It can use the debug provider, or Play Integrity if staging should mirror release. Alternatively, point the source set at the debug sources with `sourceSets["staging"].java.srcDir("src/debug/java")`. Then add a CI step that compiles the staging variant. That step needs a staging config the placeholder guard accepts, or a CI-only bypass of the guard.

### M1 — The trusted function prices trackers without a per-tracker price at zero (confirmed, latent)

`functions/index.js` `snapshotFromConfig` stamps `unitPrice: cfg.pricePerUnit ?? null`. Both clients resolve a missing price to the profile default when they stamp a snapshot: web `smokingCalculator.js:486` and Kotlin `SmokingCalculator.kt:473`. `calculateDailyFinancials` treats a `null` stamped price as *unknown*. Probe result for a tracker with `pricePerUnit: null`, 3 units, limit 10, on the current day:

```
credit {wasted: 0, saved: 0, smokingUnits: 3}  unresolved {spent: true, saved: true}
```

On an OPTION_B account, every tap on such a tracker therefore earns no money. The stamp is frozen once the day closes, so the loss cannot be recovered. `MANUAL_CREATE` uses `computeDayCredit`, which *does* fall back to the default price, so the log's `aggregateCredit` and the canonical credit disagree. This is latent: production runs on Spark and the functions are not deployed. Older configs created before the price field existed can still carry `null` (`Models.kt:231` defaults it to `null`).

**Fix:** stamp `cfg.pricePerUnit ?? defaultUnitPrice` in `index.js` `snapshotFromConfig`, to match the clients. Add a `financial.test.js` / emulator case with `pricePerUnit: null`. Every current test passes an explicit price.

### M2 — Counter operations accept any past date (latent)

`COUNTER_INCREMENT`/`COUNTER_DECREMENT` only call `requireTrackingDate`, which rejects future dates but nothing older. A call for a date in the past:

- writes `snapshotFromConfig(cfg)` from the **live** config into `days/{date}.trackerSnapshots`. `calculateDailyFinancials` then treats that stamp as dated historical truth (`stored(id)`). This bypasses the "live config only for the current date" rule that `financial.js` enforces everywhere else.
- creates an `open` day that nothing closes, because `STALE_DAY_RECONCILE` is explicitly blocked.

`DAY_CLOSE` similarly accepts the current (still open) day and re-closes days that are already closed.

**Fix:** require `date === currentTrackingDate` for counter ops. Late taps on a closed day go through `HISTORICAL_DAY_UPDATE`, which the LEGACY `applyLateCounterWrite` path mirrors. Decide whether `DAY_CLOSE` on the current date is allowed, and make a repeat close a no-op.

### L1 — A repeat `DAY_CLOSE` on a folded date can drift lifetime totals (plausible)

When `ledger.foldedIntoLifetime === true`, the `DAY_CLOSE` branch overwrites `canonicalCredit` with the freshly computed `fin.canonicalCredit`. It does not apply the old-to-new delta to `lifetimeAggregates`. `creditToFold` is computed but unused on that path. Any recomputation difference between the two closes leaves the ledger and lifetime totals inconsistent. All other operations go through `writeLedgerAndLifetime`, which does apply the delta.

**Fix:** return early (idempotent) when the day is already closed and folded, or route the folded case through `writeLedgerAndLifetime`.

### L2 — `deleteAccountData` deletes before it fences (latent)

The callable runs `recursiveDelete(users/{uid})` first and writes the `{deleting: true}` tombstone afterwards. The client wipes do it the other way round: fence first, then drain (#83). During the server wipe, another signed-in device can still write `configs` and `meta`, which are not `financialLocked`. Once the profile document is gone, it can also recreate a LEGACY profile through `validCreateProfile`. Documents written in that window survive under the final tombstone.

**Fix:** `set({deleting: true}, {merge: true})` first, then delete each subcollection (`listCollections()` + `recursiveDelete`), then overwrite with the bare tombstone.

### L3 — Unvalidated day-document metadata

`validDayUpdate` validates `updatedTrackerId` only when `counts` changes. It never type-checks `createdAt`/`updatedAt`/`closedAt`. An owner can park an arbitrary value of up to about 1 MiB in their own day document. Under the stated threat model (an owner can misstate their own data) this only affects that owner's own storage. It is cheap to bound with `updatedTrackerId is string && size() <= 64`, if the expression budget allows.

### Info

- **Android `targetSdk` 36 vs `compileSdk` 37** (lint `OldTargetApi`). Plan the bump with a behaviour-change review.
- **Lint `AcceptsUserCertificates`** is a false positive: the file is `src/debug/res/xml/network_security_config_debug.xml` and is not in the release variant.
- **The OPTION_B time zone is stored once and never updated.** Both the server and the clients use the stored `profile.timeZone`. The web "today" UI (`App.jsx:240`) uses the device zone, so a travelling OPTION_B user would see a different day from the one their taps land on. This is latent and only applies behind `VITE_OPTION_B_LEDGER`.

## Not findings (checked)

- **Rules:** cross-user isolation, the one-way `financialMode` / `status` / `foldedIntoLifetime` transitions, the deletion tombstone (it cannot drop `financialMode` and cannot be removed by the client), the trusted-only `trustedOperations` / `trustedDeletedLogs`, and the lease fences.
- **Functions:** uid comes only from auth, `operationId` and `trackerId` charset/length are validated, the mode guard runs before the receipt lookup, `migrateAccount` requires the admin claim and defaults to a dry run, and `deleteAccountData` requires a recent login.
- **Hosting:** CSP, HSTS, frame-ancestors, nosniff and Permissions-Policy are set. The bare `firebase deploy` functions guard is in place.
- **Android:** `allowBackup=false`, backup and device-transfer exclusions, release minify/shrink, and the App Check provider split between debug and release.
- **CI:** actions are pinned to SHAs, workflow permissions default to `contents: read`, lockfile integrity is validated, and the prod audit gate is in place.
