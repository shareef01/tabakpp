# Engineering audit — 4 November 2026

Branch `fix/audit-2026-11-04`, cut from `origin/main` @ `61c28d4`. Nothing has
been deployed, no Firebase resource was touched, and the financial mode is
unchanged (production remains **LEGACY**).

## A. Executive summary

Engineering quality is high. Architecture, invariants and test coverage are
unusually well documented, and the Firestore rules and trusted-backend paths
are well defended. Every one of the 12 candidate findings was traced in code.
**9 were confirmed defects and are now fixed with regression tests.** One
was a design limitation, now documented (F-07). One was a documented
architecture boundary, not a vulnerability (F-04). One was an undocumented
but intentional divergence, now documented (F-08).

The highest-impact defects, all affecting the deployed LEGACY web and Android
clients:

1. **F-01** — Undo across a day boundary reversed the *wrong* day, or silently
   did nothing while the user believed the increment was undone.
2. **F-05/F-02** — sync failures were hidden: a healthy listener cleared another
   listener's fatal error, and a dead live-day listener never reached the UI, so
   counts could be frozen with no indication.
3. **F-11** — a release that failed after its tag push could never be retried.

**Release assessment: Ready after the fixes on this branch are merged** (see F).

## C. Implemented fixes

**F-01 Undo pinned to the original date.** `useRegistry.increment` now returns
`{ trackingDate, operationId }`, and the new `undoIncrement(id, date)` uses
the ordinary optimistic decrement when the date is unchanged. Otherwise it
writes `adjustCounter(..., -1, originalDate)`. That path already reconciles a
past day that is open, or closed and folded (late write), and the backend
accepts the previous date within its 5-minute grace window. Android
`increment` passes the date to `onSuccess`, and `undoIncrement(id, date)`
mirrors the web logic. *Safe because* the same-date path is byte-for-byte the
old decrement, and the cross-date path reuses the existing, tested late-write
transaction. Files: `useRegistry.js`, `App.jsx`, `errorHandlers.js` (adds a
`DAY_CLOSED` message), `RegistryViewModel.kt`, `TrackScreen.kt`.

**F-02/F-05 Independent listener errors.** A `listenerErrors` map is keyed by
listener. Each key is cleared only by that listener's own success, and a
successful mutation clears only the mutation error. `syncError` is exposed,
and the error banner gains **Retry** (bumps `listenerEpoch`). The live-day and
ledger effects now re-subscribe on `listenerEpoch`. *Safe because* the
exposed `registryError` keeps its contract (a mutation error, else the first
sync error), and `SyncFailedState` gating is unchanged.

**F-03 No legacy fallback for non-LEGACY money.** For MIGRATING/OPTION_B
accounts, while the ledger is loading or failed, money fields are `null`,
`todayAvailable` is `false` and `financialComplete` is `false`. A failure
raises a ledger sync error with Retry. LEGACY output is identical (tested).

**F-09 Rejected adds keep the form open.** At the cap the hook throws
`TRACKER_LIMIT`, and a concurrent second add returns the *same* in-flight
promise. The form shows `mapFirestoreError(e)`. Android `addTracker` returns
`Boolean`, and both sheets close only on `true`.

**F-10 Zero pouch price preserved.** `defaultPouchPrice` (web) and
`pouchPriceText` (Android) keep a saved POUCH price, including 0, and suggest
6.50 only for accounts that never saved POUCH economics. A PACK save writes
`pouchPrice: 0`, meaning "not configured". The CSV call now uses `??`.

**F-06 Export consistency.** `readCompleteExportSnapshot` re-reads the
profile after all collections and retries (up to 3 passes) if
`lifetimeAggregates`, `financialMode` or `deleting` moved. It returns
`consistency: { stable, attempts }`, and Settings warns instead of reporting
a clean success when `stable` is false.

**F-11 Recoverable, idempotent release.** The new
`.github/scripts/resolve-release-tag.py` handles three cases:
- No tag: release main HEAD.
- Tag with a complete release: refuse.
- Tag with no release, a draft, or a partial release: resume at the commit the
  tag already points to (it must be an ancestor of main). `require-ci`
  re-validates that commit, including the exact-SHA CI check.

The tag step reuses a tag already at the validated SHA and refuses one at any
other commit. The release step sets `overwrite_files: true` so a partial
release is completed in place. No tag is ever moved or deleted.

## D. Remaining risks

- **Deferred (needs approval):** a storage-level tracker cap (F-07);
  see [proposals-f07-f08.md](proposals-f07-f08.md) for options;
  LEGACY→OPTION_B closed-day semantics (F-08). (A-1, A-2 and the Android
  export of `dailyFinancials` were fixed after the audit.)
- **Architectural limits:** LEGACY totals are owner-controlled (F-04). There is
  no App Check, so abuse resistance relies on API-key restrictions. Export is
  not atomic; inconsistency is now detected for lifetime-moving changes, but
  open-day taps mid-export can still differ by the taps themselves.
- **Not verified here:** the Android instrumentation tests
  (`android-integration.yml`, which needs an emulator and device) and a live
  release dry run. The release-script logic is unit-tested with simulated
  `git`/`gh`; the workflow YAML itself only runs on GitHub. A browser check was
  skipped because the demo build stubs `useRegistry`, so the changed logic
  cannot run there.
