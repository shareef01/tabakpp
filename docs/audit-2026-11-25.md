Base commit **`895b4a8`** on `main` (release `v1.0.20`). Branch `audit/2026-11-25-spark-isolation`.
This is a delta audit on top of the [2026-11-16 audit](audit-2026-11-16.md) and the
[2026-11-12 master audit](audit-2026-11-12/TABAKPP_MASTER_AUDIT.md). It focuses on the
Spark-only architecture boundary: how much of the parked Option B (Cloud Functions) code

local suite.

## Summary

No Critical or High findings. The production data path, the rules and the domain logic
were re-checked and are sound. The main finding is that the parked, undeployed Option B
backend still shipped in three production places:

- the always-loaded web `firebase` chunk;
- the production `firebase.json` (a `functions` target and a Functions emulator);
- the production hosting CSP.

None of them was reachable by a production account, but each one was unnecessary exposure,
download weight or a deploy footgun. All three are fixed.

## Findings

### F-01: Functions SDK shipped to every web user (fixed)

**Evidence.**

- `webApp/src/services/trustedFinancial.js` imported `firebase/functions` statically.
- `registryService.js` imports `trustedFinancial.js`, so the SDK was part of the eagerly
  loaded `firebase` chunk. The built chunk contained the `cloudfunctions.net` URL builder.
- A callable is reached only for `MIGRATING`/`OPTION_B` accounts. The rules forbid a client
  from ever setting those modes (`firestore.rules`: a client-created profile is `LEGACY`,
  and `financialMode` is excluded from client updates). Only the undeployed Admin-SDK
  migration could set them. So on production this code was dead.

**Fix.**

- `trustedFinancial.js` now loads `firebase/functions` with a dynamic `import()` on first use.
  A failed chunk fetch resets the cached promise, so the next call can retry.
- `vite.config.js` puts the SDK in its own `firebase-functions` chunk and keeps it out of the
  service-worker precache.

**Measured (production build, same machine):**

| | Before | After |
|---|---|---|
| `firebase` chunk (always loaded) | 591.02 kB / 176.96 kB gzip | 582.90 kB / 174.22 kB gzip |
| Functions SDK | inside `firebase` | `firebase-functions` 8.34 kB, lazy, not precached |
| Precache | 43 entries, 2232.23 KiB | 43 entries, 2224.81 KiB |

**Regression coverage.** `trustedFinancial.test.js` now asserts that importing the module
neither loads nor initialises the SDK. The region test still passes. The Option B routing
suites (`closeDayRouting`, `deleteAccountRouting`) pass unchanged.

### F-02: Parked functions in the production Firebase config (fixed)

**Evidence.**

- `firebase.json` carried a `functions` target and a `functions` emulator. A bare
  `firebase deploy` therefore included functions. Only the predeploy guard
  (`scripts/guard-functions-deploy.mjs`) stopped it.
- The production CSP `connect-src` allowed `https://europe-west1-tabakpp-ff036.cloudfunctions.net`,
  an origin with nothing deployed behind it.

**Fix.**

- The `functions` block and the Functions emulator moved to a new experimental
  `firebase.functions.json`. It has no hosting, keeps the predeploy guard, and is now used by
  the CI `functions` job.
- The production `firebase.json` has no functions target at all, so ordinary release
  commands cannot even attempt a Functions deploy. The guard remains as a second barrier for
  the experimental config.
- The Cloud Functions origin was removed from the production CSP. The staging CSP keeps its
  own staging origin on purpose: staging is where Option B would be exercised, and an
  existing test requires it.
- Docs updated: `SETUP_GUIDE.md` has a new "Option B Cloud Functions" section, and the
  README repository map and the guard's messages were changed.

**Rules unaffected.** `financialLocked` and the `MIGRATING`/`OPTION_B` invariants are kept
unchanged. They are historical security invariants and cost nothing on Spark.

**Regression coverage.**

- `staging-isolation.test.mjs` now asserts that production `firebase.json` has no
  `functions` block, no Functions emulator, and no `cloudfunctions.net` in the CSP.
- It also asserts that `firebase.functions.json` has no hosting and keeps the guard.
- A negative control (re-adding the origin) made the suite fail (1 failed / 24 passed),
  and the file was restored.
- The functions emulator integration ran green through the new config: 30 / 30 suites.

### F-03: Required-checks claim in README was stale (fixed)

`README.md` said `functions`, `test` and `validate-action-pins` were advisory. The GitHub API
(`branches/main/protection/required_status_checks`) returns all five as required, with
`strict: true`. This matches CI-1 in the 2026-11-16 audit. The README now says so.

### F-04: Option B gateway compiled into the Android APK (accepted)

`shared` depends on `dev.gitlive:firebase-functions`, and Koin wires `FirebaseTrustedFinancial`
with `optionBLedgerEnabled = true`. Routing still needs the server-side mode to be
`OPTION_B` (`RegistryViewModel.kt:691`), which a client cannot set. So production never
calls it, and the native SDK only connects when a callable is invoked. Removing it would also
remove coverage that the instrumentation suite (`FirebaseRegistryRepositoryTest`) relies on.
It is kept, and documented here.

### F-05: Firestore reads per web cold start (accepted, estimate)

Per web cold start, one `LEGACY` user with *N* day docs and *M* log docs reads about:

- profile, avatar and today's day doc: 3 reads;
- configs: up to 8;
- the `days` window: min(*N*, 400);
- the `logs` window: min(*M*, 1200);
- the open-day reconcile query and the backfill marker: about 2.

Each tap is one transaction: about 1–2 reads and 1 write. No receipt documents are written
for `LEGACY` accounts.

| Scenario | Reads / day | Writes / day | Share of the Spark limits (50k reads, 20k writes) |
|---|---|---|---|
| 1 year of history (365 days, 50 logs), 10 cold starts a day across 2 devices, 25 taps | ≈ 4.3k + 50 | ≈ 30 | ≈ 9% reads, < 1% writes |
| 2 years (730 days, but the window caps at 400), 20 cold starts | ≈ 9.3k | ≈ 30 | ≈ 19% reads |

The free tier is comfortable for one person. The cost driver is cold starts, not taps.

`persistentLocalCache` was considered again and rejected. It saves reads only for reopens
within about 30 minutes (Firestore bills a full re-query after that). It also keeps
sensitive tracking data in IndexedDB on shared devices, and it adds multi-tab coordination.
Those costs outweigh a single-digit percentage of one project's quota. The decision is
unchanged from the 2026-11-12 performance audit.

### F-06: Timeouts caused by the audit's own parallel runs (closed)

The cause was how the audit scheduled its runs. Both times, I ran the web suite as a
background job next to a Gradle task on the same machine:

| Run | Ran alongside | Result | Same suite, run alone |
|---|---|---|---|
| Baseline | `gradlew testDebugUnitTest` | 624 / 625: the History paging test timed out | that file 3 / 3; next full run 627 / 627 |
| UI polish pass (#185) | `gradlew :androidApp:lintDebug` | 630 / 632: the History paging test and an `AuthScreen` test timed out | 632 / 632 |

Both suites pass in CI and whenever they run alone. The tests themselves need no change.
An earlier version of this entry suggested raising the paging test's timeout; that was
wrong, and it would only have hidden real slowness later. If a timeout appears again, re-run
the suite alone before treating it as a flake.

### F-07: XP and rank (owner decision)

`calculateXP` counts distinct tracked days plus the goal streak. It rewards consistent
logging, not consumption, and the goal streak needs every day to stay within target.
The audit brief asks that consumption is not gamified. This does not reward smoking, so it
was left alone. Renaming the ranks or hiding XP is a product call for the owner.

## Re-checked, no defect found

- **Account isolation:** `useRegistry` clears every piece of state on a uid change before it
  attaches new listeners. Web Firestore uses the memory cache. `localStorage` holds only the
  last accent and the build id; `sessionStorage` holds only the auth-intent flag.
- **Service worker:** same-origin routes only. HTML is network-only with a revisioned
  offline fallback. No Firestore or Auth traffic is cached.
- **Missing days:** the goal streak breaks on a day with no record
  (`calculateStreak`: `cursor !== trackingDay && !dayCounts`). A day with no data is never
  counted as a day within target.
- **CSV export:** user-originated strings are neutralised against formula injection on both
  web and Kotlin. There is no import feature, so the import hardening in the brief does not
  apply.
- **Offline:** counter, history and tracker-delete writes stay online-only (`requireOnline`),
  with explicit messages. Tracker config edits may queue, and pending configs are flagged in
  the UI. Online-only logging is kept deliberately (see the 2026-11-12 data-integrity
  audit). A durable offline queue would need account-scoped replay, tombstone awareness and
  date pinning, all on top of transactions that read before they write. That is a large
  integrity risk for a personal app, so it was not built.
