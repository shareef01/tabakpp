# Engineering audit — 9 November 2026

Scope: `main` at **`34fdcb3`** (release `v1.0.14`), plus the local working tree
used for this audit. No Firebase project, release, migration or production data
was touched. Production remains the Firebase **Spark** plan with `LEGACY`
financial mode; the Option B Cloud Functions are still written and tested but
**not deployed**.

This is the current audit. [`REPOSITORY_AUDIT.md`](REPOSITORY_AUDIT.md) is a
historical snapshot at `v1.0.9`.

---

## A. Executive summary

The repository is in unusually good shape for a personal portfolio project.
Architecture, security-rule coverage, cross-platform contract fixtures and the
release gate are stronger than the documentation suggests. No cross-user
authorization bypass, data-loss defect or broken build was found.

The confirmed issues in this pass were smaller:

- **Portfolio accuracy (High):** the README still advertised `v1.0.9` while the
  repository was at `v1.0.14`; the case study repeated stale test counts and
  described a closed day as wholly immutable (its stamped configuration is
  frozen, but its counts remain deliberately owner-editable).
- **Misleading UI (Medium):** the manual-entry form collapsed every rejection
  (tracker cap, future date, invalid date) into “check your connection”, and its
  inline error was not announced to assistive technology.
- **Misleading destructive copy (Low):** deleting a tracker said “logged history
  stays available”, although the current open day’s counts for that tracker are
  removed by design.
- **Developer experience (Low):** the action-pin CI scripts crashed on a
  Windows `cp1252` console because they print status glyphs.

All four were fixed with focused changes. The financial and security concerns in
the audit brief were investigated and are documented below as accepted
limitations, not silently changed.

## C. Verification of the known concerns

### 1. Financial calculations — multiple manual entries on one date

**Confirmed behaviour, not an undocumented defect.** The LEGACY `logs` path
stamps one credit per record (`createManualEntry` builds `computeDayCredit` from
that record’s counts and every tracker snapshot). Two manual entries on one date
therefore each receive the day’s full target allowance. This is pinned by
`registryService.test.js` → “Option A: two manual entries on one date credit the
daily allowance twice (accepted limitation)” and documented in
`docs/financial-semantics.md` §3–§4.

`wasted` and `smokingUnits` remain event-additive and correct. The Option B
backend already computes one allowance per date (`functions/financial.test.js` →
“one allowance per date … saved €5, not €15”).

**Not changed:** adopting Option B on the LEGACY path needs a write-path change,
a mixed-client compatibility window and an authorised historical repair. It is
explicitly **DEFERRED_APPROVAL** in `docs/release-hardening/BACKLOG.md`
(AUDIT-10-07). No stored record was rewritten.

### 2. Security and accounting integrity

- Every user path is guarded by `isOwner(userId)`; the catch-all
  `match /{document=**} { allow read, write: if false; }` remains.
- Settings, mutation and day-document writes have separate shape validators;
  closed-day `trackerSnapshots`, `status` and `foldedIntoLifetime` are one-way.
- Client-created profiles must start `LEGACY`; `MIGRATING`/`OPTION_B` are
  server-owned.
- The rules suite passed **180 tests** against the emulator, including denial
  cases and cross-user reads/writes.
- The accepted Spark residual is unchanged: an owner can rewrite their own
  `counts`/`aggregateCredit`, because rules cannot recompute money and no server
  is deployed. That is documented in `README.md`, `SECURITY.md` and
  `docs/financial-semantics.md`.

No authorization defect was found.

### 3. Multi-device tracker limits

The cross-device creation race still exists. `addProtocol` reads the config
count, then writes a new auto-id document; two devices can both pass the check.
The effect is bounded and fail-closed at use time: `adjustCounter` and
`createManualEntry` reject a 9th tracker (`TRACKER_LIMIT`), and the day’s
`trackerSnapshots` map is capped at 8 by rules. A storage-level guarantee needs
a server-side counter or a schema migration. A compensating client-side delete
was deliberately not added: it can race and remove the wrong tracker, and
config deletes are unavailable to locked accounts.

**Accepted limitation**, documented in `README.md` (“Up to 8 trackers”) and
`docs/audit-2026-11-04.md` F-07.

### 4. Offline behaviour

- The live write paths (`adjustCounter`, manual/history writes, close day)
  require `navigator.onLine` before starting; Firestore transactions do not
  queue offline.
- Writes resolve only after the backend acknowledges them; the UI shows
  “Saving…” during the await and closes/toasts only on success. No path displays
  a successful save before commit.
- The PWA shell is cached and opens offline; writes are not queued.
- The emulator suite `offlineBehavior.emulator.test.js` proves a plain write and
  `addProtocol` stay pending while offline and resolve on reconnect.

**Accepted limitation**, stated in `README.md` and the case study: logging needs
a connection. No offline write queue was added (a fake queue would risk double
counting).

### 5. Data export

- `readCompleteExportSnapshot` reads profile, meta, configs, days, logs and
  ledgers with keyset pagination; it is not limited by the UI’s 400-day / 1,200-
  log listener windows.
- It re-reads the profile after the pass and retries up to three times if
  `lifetimeAggregates`, `financialMode` or `deleting` changed; it returns
  `consistency.stable`.
- Settings warns instead of claiming a clean export when `stable === false`.
- Known limit: an open-day counter tap during the pass does not move
  `lifetimeAggregates`, so it is not detected. Such a tap cannot make the
  lifetime total internally inconsistent; it only means the exported snapshot is
  “as of slightly different instants”. Documented in `registryService.js` and
  the case study.

### 6. Documentation

Corrected in this pass: README release, build-variant count, case-study release
and test counts, closed-day wording, and the historical status of
`REPOSITORY_AUDIT.md`. A “See it” section now links the live PWA, APK and
screenshots from the case study.

Claims still verified as accurate:

- Closed-day stamped configuration is frozen; counts remain owner-editable.
- Five CI jobs exist; two (`mobile`, `web-and-rules`) are required on `main`.
- Android has three build variants (debug, release, staging).
- Firebase Spark is the production plan; Functions are not deployed.
- App Check is not used and API-key restrictions are not presented as a
  substitute for authorization.
- Contract fixtures are 76 assertions.

## F. Accepted limitations (Spark, unchanged)

1. **No server-authoritative LEGACY money.** Rules validate ownership and shape,
   not arithmetic. An owner can rewrite their own totals. Option B is
   implemented and CI-tested but not deployed because it needs Blaze.
2. **No App Check.** A modified client can act as its own signed-in user, never
   as another user. API-key restrictions are defence in depth, not attestation.
3. **Tracker cap is enforced per write, not by a collection counter.** The
   cross-device creation race is bounded and fail-closed at day-write time.
4. **No offline write queue.** Firestore transactions need the network; the PWA
   shell opens offline.
5. **Event-level manual-entry allowances (Option A).** Multiple manual entries
   on one date can credit the target allowance more than once. Documented and
   pinned; changing it requires product approval and a repair plan.
6. **Export is not an atomic multi-collection snapshot.** Lifetime-moving
   changes are detected and retried; open-day taps are not.

None of these requires a paid service, a schema migration or a destructive data
change.
